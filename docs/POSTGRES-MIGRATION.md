# D1 to PostgreSQL with Hyperdrive

**Status — production cutover completed September 27, 2026:** The main Folio Worker and public-index Worker now read PlanetScale PostgreSQL 18 through separate cache-disabled Cloudflare Hyperdrive configurations. A final maintenance-window D1 export was imported with full-row verification; an independent **post-commit** comparison matched all stored fields in 32 tables and 832 rows. D1 and its private exports remain intact as rollback sources. Hosted public and anonymous-access smoke checks passed; a live owner sign-in, owner-scoped write, and paid-provider run were **not** performed as part of the cutover.

A database *transaction* makes a set of writes all-or-nothing. Folio uses D1's `batch()` for operations such as saving an API request together with its paid-run reservation. If the second write fails, the first must disappear too; otherwise a retry could be charged twice or a quota could be bypassed. The PostgreSQL bridge executes each batch inside `BEGIN`/`COMMIT` and rolls it back on error. It also locks the single `folio_write_gate` row for each Folio write transaction so concurrent count-then-insert reservations retain D1's serialized behavior. This is a compatibility step, not a claim that arbitrary SQLite SQL works in PostgreSQL.

## What is implemented

- `migrations/postgres/0001_schema.sql` represents the final state of D1 migrations `0001`–`0021`, including auth tables, published question snapshots, constraints, indexes, evidence-deletion behavior, cost observations, and the supported JSON read functions. Existing millisecond timestamps and JSON text remain in their original representation; `user.email_verified` becomes a PostgreSQL boolean.
- `src/lib/db.ts` uses a request-scoped Hyperdrive connection when a `HYPERDRIVE` binding exists. Otherwise local development can use its D1 binding; production has no D1 binding after the post-cutover cleanup. Local development may opt into an isolated PostgreSQL connection with `FOLIO_POSTGRES_URL`; this is not a production bypass.
- `src/lib/pg-d1.ts` adapts the existing store interface, positional placeholders, transaction batches, and numeric results. Better Auth uses a separate PostgreSQL Drizzle schema when PostgreSQL is selected. The public-index Worker has its own Hyperdrive configuration and a separate database role with `SELECT` only on `published_question_snapshots`; private-table reads and snapshot updates were denied in a live credential check. Its default transactions are read-only. The main Worker retains the write-capable application role.
- `scripts/migrate-d1-to-postgres.py` reads a private D1 SQL export into a temporary SQLite database, refuses unknown or mismatched tables, imports into an **empty PostgreSQL public schema**, and verifies every imported field inside one transaction. Local mode requires a Unix socket and commits after verification. Remote mode reads an owner-only URL file, uses verified TLS, and **rolls back by default**; only `--commit-remote` commits after verification. A failed check rolls the destination transaction back. The script does not print account rows, evidence, credentials, or SQL errors that could contain private values.

The D1 SQL export may omit hidden SQLite `rowid` values. The importer reconstructs rowids for three historical cost-view branches; it preserves explicit IDs, fields, relationships, and identity sequence watermarks. Do not treat a reconstructed hidden rowid as a stable external ID.

## Local verification

Use an isolated local PostgreSQL server on port `55432`, never a production connection, for `bun run test:pg`. The test rejects other hosts and ports. The import tests create and remove their own disposable local databases.

```sh
python3 tests/postgres-import.test.py -v
FOLIO_PG_TEST_URL='postgresql://127.0.0.1:55432/postgres' bun run test:pg
bun run typecheck
bun run test
bun run test:d1
bun run cf:build
```

At the initial rehearsal, these passed: three importer tests, one local PostgreSQL runtime integration test (auth, concurrent paid-run gate, batch rollback, JSON read), type checking, 340 unit tests, 36 D1 integration tests, and the Cloudflare build. A fresh local D1 backup and a private read-only production D1 snapshot imported locally with full-row verification; a read-only cost/evaluation smoke check on the local copy passed. Subsequently, a production rehearsal snapshot passed full-row verification in a **rolled-back PlanetScale transaction**; a disposable Worker queried its PostgreSQL 18 server through cache-disabled Hyperdrive. The final paused-write snapshot was separately imported and verified after commit. Local tests and hosted smoke checks do not establish live owner sign-in, new paid-provider outcomes, or long-term production behavior.

## Production cutover record and remaining checks

1. **Credential and compatibility.** The user authorized the scoped PlanetScale credential. It was kept in an ignored owner-only local file and the necessary Hyperdrive origin configuration, never in Git or printed output. Rotate it now that the cutover is complete because it was pasted into chat. [Cloudflare's generic PostgreSQL table lists `9.0`–`17.x` as known supported, while its PlanetScale provider row says all versions](https://developers.cloudflare.com/hyperdrive/reference/supported-databases-and-features/); the supplied target reports `18.0.6`. A real Hyperdrive Worker query, full public-index read, and transaction/row-lock rollback passed on 18, but formal provider compatibility confirmation and ongoing monitoring remain prudent. Hyperdrive caching is disabled. Its `require` TLS mode uses [WebPKI certificate validation](https://developers.cloudflare.com/hyperdrive/configuration/tls-ssl-certificates-for-hyperdrive/); `verify-full` requires an uploaded CA certificate.
2. **Pause and snapshot.** With no running paid evaluations or keyword runs and the scheduler disabled, temporary maintenance Workers returned 503 for the main site, write API, and public-index route. Wrangler's D1 export can briefly make D1 unavailable and prints a short-lived signed download URL; both export logs and SQL files were kept private with restrictive permissions. Two exports taken under maintenance were byte-identical. The earlier read-only export was rehearsal only.
3. **Import and independent verification.** The final export passed the importer's default remote verify-and-rollback mode, then `--commit-remote` committed to an empty PlanetScale `public` schema only after every field matched. A separate post-commit comparison matched **32 tables, 832 rows, all stored fields**; published question snapshots were included. The importer refuses unexpected source tables and nonempty destinations. D1 was not deleted or overwritten.
4. **Switch and hosted checks.** The main app first ran on PostgreSQL behind a read-only wrapper; public pages and benchmark data returned 200, anonymous private data returned 401, and writes stayed 503. The public-index Worker then switched to Hyperdrive and served three published snapshots. The normal main Worker was deployed last. After release, `/`, `/privacy`, `/login`, `/overview`, `/pricing`, `/api/public/benchmarks`, `/leaderboard?view=questions`, and `/api/question-index` returned 200; anonymous private site, evaluation, benchmark, SEO, and cost routes returned 401; `/api/auth/get-session` returned 200. A disposable Hyperdrive Worker acquired the `folio_write_gate` row lock and rolled back a no-op update, leaving it intact. No new paid provider job was started to test storage.
5. **Rollback and unfinished validation.** The production D1 bindings were removed after the UI restoration; the frozen D1 database and private exports remain intact. If a fault appears, pause writes first, compare any new PostgreSQL writes with the frozen D1 snapshot, and reconcile them before re-adding D1 bindings and removing Hyperdrive from **both** Workers; switching back blindly could lose post-cutover records. Live owner sign-in, owner-scoped reads/writes, background reconciliation, and longer-running read-after-write/latency/error monitoring remain to be checked. The public-index Worker now uses its separately verified read-only role; rotation of the main agent-scoped credential remains an operational follow-up. Local fixtures and anonymous hosted smoke checks are not a substitute for those live validations.
