# Moving Folio to Postgres

Status: **plan**. The app runs on Cloudflare D1 today. This document describes a full migration to PlanetScale Postgres (`folio`, branch `main`, `ap-southeast-2`), in an order that keeps the risky parts — authentication and paid reservations — last.

Scope measured from the repository:

| Surface | Count | Consequence |
| --- | ---: | --- |
| `.prepare()` call sites | 132 across 30 files | all must keep working |
| Migrations | 24 SQLite files | need Postgres DDL + a data copy |
| `json_extract(...)` uses | 40 | rewrite to `->>` / `jsonb` |
| `INSERT OR IGNORE` | 10 | rewrite to `ON CONFLICT DO NOTHING` |
| `unixepoch()` / `strftime` / `datetime()` | 13 | rewrite to `to_timestamp` / `EXTRACT` |
| 2-argument `MAX(a,b)` | 6 | rewrite to `GREATEST` (aggregate `MAX` stays) |
| SQLite triggers | 20 | need `plpgsql` functions + triggers |
| `AUTOINCREMENT` columns | 2 | `GENERATED BY DEFAULT AS IDENTITY` |
| `meta.changes` reads | 16 | map from `rowCount` |
| `RETURNING` | 36 | supported by Postgres as-is |

## The decision that keeps this cheap

Every store talks to D1 through the same small surface: `db.prepare(sql).bind(...)` followed by `.first()`, `.all()` or `.run()`, with `run()` read for `meta.changes`. Rather than edit 132 call sites, ship a **D1-shaped adapter over `pg`**:

- `src/lib/pg/compat.ts` — pure SQL translation: `?` → `$n`, the SQLite functions above, `INSERT OR IGNORE`, and 2-argument `MAX`/`MIN`.
- `src/lib/pg/database.ts` — a `PgDatabase` that returns `{ first, all, run }` with the same result shapes D1 returns.

Then each store moves by changing one import, not its SQL. The adapter is tested on its own (pure translation) and against a real Postgres schema, so a ported store can be proven before it is enabled.

## Phases

**0. Foundations (days, not weeks).**
Add `pg`, a `DB_ENGINE` switch (`d1` default, `postgres` opt-in), the compat layer with unit tests, and a `folio_test` schema on the PlanetScale instance for integration tests. Nothing user-facing changes.

**1. Schema parity.**
Translate the 24 migrations to Postgres DDL: text types, `bigint` for millisecond timestamps, identity columns, `plpgsql` triggers for the 20 immutability/guard triggers, and a `pg_migrations` journal. Copy the September snapshot into `folio_test` to test against real data. Acceptance: every table exists, every trigger fires, a row-by-row checksum of a few tables matches.

**2. Stores, lowest risk first.**
Order: `seo-store` → `sites`/`scans` → `eval-store` → keyword stores → MCP/agent-api stores → search console. For each: port behind the switch, run its unit tests on both engines, then run the 37 real-D1 integration cases against Postgres equivalents. A store is "done" only when both engines pass.

**3. Dual-run verification (staging only).**
With `DB_ENGINE=postgres`, replay a set of representative reads against both databases and diff the results. Any divergence is a compat bug, not a data bug — this is the phase that catches `json_extract` casting and boolean handling.

**4. Cut writes over.**
Flip write paths store by store behind the flag; freeze the D1 copies read-only as they flip. Paid reservations (`rate_limit`, `agent_tool_calls`, `seo_agent_requests`) move only after their concurrency tests pass on Postgres, because those rely on conditional `UPDATE … RETURNING` returning exactly one row.

**5. Authentication last.**
Swap the Better Auth drizzle adapter to `pg`, run the auth integration suite (sign-up, sign-in, session read, sign-out, account deletion cascade), then cut over. Expect sessions to be re-created; do it in a maintenance window with the D1 `session` table readable as a fallback. This is the only step that can lock users out, which is why it is last and reversible.

**6. Retire D1.**
Keep a final export, remove the binding from `wrangler.jsonc`, delete the D1 database after a retention period, and keep `docs/LOCAL-D1.md` as history rather than instructions.

## Runtime changes

- Workers reach Postgres through **Hyperdrive**: add a `hyperdrive` binding in `wrangler.jsonc`, connect with `pg` under `nodejs_compat`, and read `env.HYPERDRIVE.connectionString`. Direct TCP is not available without it.
- Local development needs either a local Postgres or the PlanetScale credential; `DB_ENGINE` decides which store the app opens.
- `pg` pooling is per-request in Workers; Hyperdrive does the pooling across requests. Do not cache a client in module scope.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| `json_extract` returns text in SQLite but typed JSON in PG | always cast (`->>`) and compare with `::int`/`::numeric`; covered by the dual-run diff |
| Boolean columns are `0/1` in SQLite | schema keeps `integer` where the code compares to `0/1`, instead of switching to `boolean` mid-migration |
| `meta.changes` semantics | adapter maps `rowCount`; the deletion trigger case (`changes` > 1) is explicitly tested |
| SQLite triggers are simpler than plpgsql | translate each of the 20 and test the abort path |
| Reservations double-charge under concurrency | port only after the two-writer race tests pass on Postgres |
| Better Auth rate limiting on Postgres | the drizzle adapter needed >= 1.7.7 (GHSA-44jh-23m7-hpcf); the repository is on 1.7.18 |
| Latency from Sydney | measure p50/p95 through Hyperdrive before cutover; keep the public index static |
| Rollback | every phase keeps D1 authoritative until the next flips; the flag reverts one store at a time |

## Definition of done

- `DB_ENGINE=postgres` passes the full unit suite, the 37 integration cases, and the browser specs that touch persistence.
- Dual-run diffs are empty for the representative read set.
- Auth flows verified on Postgres in staging before cutover.
- D1 frozen, exported, and removed from configuration after the retention period.

## Phase 1 result: schema parity

`scripts/pg-schema.ts` translates the 24 SQLite migrations and applies them to a fresh schema; `scripts/pg-parity.ts` compares the result with D1.

| Result | Count |
| --- | ---: |
| Statements executed | 84 |
| Failures | 0 |
| Tables in `folio_pg` | 31 |
| Columns differing from D1 | 0 |
| Triggers translated | 13 |
| Statements needing a hand port | 9 views, 4 cost-accounting triggers, 2 cost backfills |

What translated mechanically: tables, indexes, `ALTER TABLE … ADD COLUMN`, identity columns, seed inserts, `json_extract`-free triggers (immutability guards, cascade deletes), `IS`/`IS NOT` value comparisons (→ `DISTINCT FROM`), `length(CAST(x AS BLOB))` (→ `octet_length`), and reserved `"user"`.

What did not, and why it is deliberate:

- **`provider_cost_latest` view** (recreated in five migrations) uses SQLite's implicit `rowid`.
- **Four cost-accounting triggers** build `provider_cost_observations` rows inside SQLite with `iif`, `json_type`, `json_extract` and `unixepoch('now')`.
- **Two backfill inserts** in the same style.

Those are the only hand-written pieces left in the schema, and they share one design question: keep cost snapshots in database triggers, or move them into an application helper that both engines can call? The second option removes 300 lines of dialect-specific SQL and makes the accounting testable, but changes where a write happens — worth deciding before porting stores that emit usage.

`json_valid` has no Postgres equivalent; `scripts/pg-schema.ts` installs a small `plpgsql` shim so `CHECK (json_valid(...))` keeps its guarantee instead of being dropped.

## Spike result

`seo-store` — three tables, seven functions — now runs on Postgres **without changing its code**, through `src/lib/pg/database.ts` and `src/lib/pg/compat.ts`:

```
reserve: example.com pending
complete: complete retrieved: true
detail saved: 1 keyword rows, 1 backlink rows
reopen: example pricing | aggregate kept: true
list: { detailState: 'collected', status: 'complete', knownCostUsd: 0.02 }
refused as expected: second detail collection
```

Repeatable as `bun run test:pg` (skips without `PLANETSCALE_APP_URL`). Three findings that change the plan:

1. **`user` is a reserved word.** SQLite accepted `CREATE TABLE user`; Postgres needs `"user"`. The compat layer now quotes the bare identifier, and the DDL translator must do the same.
2. **Timestamps must be `bigint`.** Milliseconds since epoch (~1.7e12) overflow `integer`. `pg` returns `int8` as text by default, so the driver needs `types.setTypeParser(20, Number)` or every `new Date(created_at)` breaks.
3. **`strftime(..., 'unixepoch')` input is seconds.** The call sites already divide by 1000 before formatting; the translation must not divide again.

## Engine switch (implemented)

`src/lib/db.ts` now chooses the store: `DB_ENGINE=postgres` returns the D1-shaped adapter over `pg`, anything else returns the D1 binding. Stores are unchanged — they still call `prepare().bind().first()/.all()/.run()`.

Authentication is the one exception and is pinned to D1 through `getAuthDb()`: Better Auth's drizzle adapter is bound to the D1 client, and a half-migrated session table is the failure that locks people out.

Verified against the application tables, not just the research ones: `sites` reads, the leaderboard's join, placeholder binding and `meta.changes` all behave through the Postgres adapter.
